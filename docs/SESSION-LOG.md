**The finding was a default, and my first conclusion was wrong.** The first pass said 100k rows was impractical: insert throughput collapsed and an `ALTER TABLE … ADD VECTOR INDEX` was still running after six minutes. 768 float32 is 3072 bytes a row, so 100k rows is 307 MB of vectors against the stock **16 MB** `mhnsw_max_cache_size` — below the working-set size the index cache thrashes and what you are timing is disk, not search. Rick raised it to 2 GiB (and the buffer pool to 4 GiB) and restarted; same binary, same fixture, same rows, **7.52 ms median became 1.42 ms** and 100k went from unreachable to eight minutes. It is `GLOBAL`-only, so no application user can set it and the product can never detect or fix it from inside. That makes it a deployment note with teeth: the default will make a user's memory store feel broken for reasons nothing in the app can explain.

**Two measurement failures worth remembering, both mine.** The synthetic fixture was `sin(seed·k + i·k₂)`; sine is periodic, so seed 1,000,020 collided with seed 6,701 and the benchmark reported `distance=0.000000` — a probe identical to a stored row is the easiest possible query for a nearest-neighbour index, and it was one commit from the write-up. Replaced with SplitMix64 per dimension, with that exact pair as a test. Then the entire 100k run was taken while the server's own update agent installed a kernel; Rick caught it before the reboot and moved the agent off the box. None of those numbers survive — everything in the write-up was re-taken on an idle server. The relative index-versus-no-index result was re-taken too, and is better for it: 959 rows/s without the index against 425 with it, **both flat**, where the confounded run had batch times climbing 659 → 3,704 ms.
