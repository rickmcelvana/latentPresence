**The finding was a default, and my first conclusion was wrong.** The first pass said 100k rows was impractical: insert throughput collapsed and an `ALTER TABLE … ADD VECTOR INDEX` was still running after six minutes. 768 float32 is 3072 bytes a row, so 100k rows is 307 MB of vectors against the stock **16 MB** `mhnsw_max_cache_size` — below the working-set size the index cache thrashes and what you are timing is disk, not search. Rick raised it to 2 GiB (and the buffer pool to 4 GiB) and restarted; same binary, same fixture, same rows, **7.52 ms median became 1.42 ms** and 100k went from unreachable to eight minutes. It is `GLOBAL`-only, so no application user can set it and the product can never detect or fix it from inside. That makes it a deployment note with teeth: the default will make a user's memory store feel broken for reasons nothing in the app can explain.

**Two measurement failures worth remembering, both mine.** The synthetic fixture was `sin(seed·k + i·k₂)`; sine is periodic, so seed 1,000,020 collided with seed 6,701 and the benchmark reported `distance=0.000000` — a probe identical to a stored row is the easiest possible query for a nearest-neighbour index, and it was one commit from the write-up. Replaced with SplitMix64 per dimension, with that exact pair as a test. Then the entire 100k run was taken while the server's own update agent installed a kernel; Rick caught it before the reboot and moved the agent off the box. None of those numbers survive — everything in the write-up was re-taken on an idle server. ### Later still — C-5 run, and the GPU question answered the hard way
**C-5, `fp32` against `q8`.** Rick gave the go for the download. Both graphs loaded in one node process through `kokoro-js` and the same three sentences synthesised twice — plain, sibilant, long held vowels, the places quantisation shows first. **No measurable difference**: loudness within 0.1 dB, noise floor within ~1 dB at −120 to −168 dBFS, high-frequency content between words unchanged. What did differ is duration — each graph predicts its own phoneme lengths, so the takes drift by up to 50 ms per utterance, which will move word timestamps and therefore visemes. `q8` is 3.4x *slower*, but only under onnxruntime-node, which dequantises int8 per operator; that is a fact about the CPU execution provider and says nothing about WebGPU. 233 MB of every user's first run rides on it, so it goes to Rick's ears as R-5.

**The first pass reported −2.5 dB SNR and it was garbage.** Because the two takes differ in length they are not sample-aligned, so a sample-wise metric measures phase drift and calls it noise. **A confident-looking number from a metric whose precondition does not hold is worse than no number**, and the rewrite is alignment-free on purpose: per-frame noise floor and zero-crossing rate in the quietest tenth of frames, which is where quantisation hiss would actually live.

**Two findings in passing, both worth more than the comparison.** `KOKORO_BYTES.q8` said 86,030,000 — that is `model_q8f16.onnx`, a file `dtype: 'q8'` never fetches. transformers.js maps a dtype to a filename *suffix*, and `q8` is `_quantized`, so the real download is `model_quantized.onnx` at 92,361,116. **The consent screen was understating a download by 6.3 MB** because the number had been read off a file listing by name-matching instead of resolved from the library. Exactly SURFACE 11's failure mode, from a source that looked authoritative. And Kokoro's output **is not bounded to [−1, 1]** — `fp32` peaked at 1.043 — so P1-T08 must clamp rather than trust the range.

**C-4, and it was not one line of a log.** Rick's Kokoro-FastAPI was on the CPU. `torch.__version__` in its venv is `2.14.0+cpu` against a `pyproject.toml` pinning `torch==2.8.0+cu128` — and the version being wrong is the tell that the pin never applied at all. Every CUDA wheel is gated on `platform_machine == 'x86_64'`; **Windows reports `AMD64`**, so the marker is false, `[gpu-cu128]` resolves to nothing, and uv quietly satisfies `kokoro`'s unversioned `torch` from PyPI. Installs clean, runs clean, wrong device.

**The log lies, and that is the transferable part.** `model_manager` prints `Initializing Kokoro V1 on cuda` from `"cuda" if settings.use_gpu else "cpu"` — it reports the environment variable and never asks torch. Only the later `Loading Kokoro model on cpu` from `settings.get_device()` is real. **The two lines disagreeing is the signature of the bug**, and Rick's pasted log contained the answer before either of us read it as one. `start-gpu.ps1` now installs the cu128 wheel explicitly — sidestepping the marker without touching an upstream file, so `git pull` stays clean — and gates the launch on an actual kernel launch rather than `is_available()`, because a wheel for the wrong architecture imports and reports available and then dies on the first operator.

**This also settles D-7's open caveat: 15.3 ms/char was a CPU number.** Every conclusion from it survives, because they all turn on the *ratio* of synthesis to speech and a faster device only widens it. ### P1-T06 — STT providers, and four facts that each changed the code
Four providers behind `STTProvider`: Moonshine and Whisper through a shared worker in `packages/ml-web/src/asr`, an `/audio/transcriptions` adapter, and a fake. Gate green at 486 TypeScript / 17 Rust, up 69.

**The work was not writing the providers, it was establishing what is true.** Each of these would have been wrong from a reasonable assumption, and each one changed code:

1. **The ASR pipeline does not resample.** `prepareAudios` passes a `Float32Array` straight through. So `resample.ts` had to exist — windowed sinc, Blackman window, low-passing on the way down, because linear interpolation folds everything above 8 kHz back into the speech band and sibilants live there.
2. **`_call_moonshine` returns `{ text }` and nothing else**, so Moonshine can never report word timings however it is asked.
3. **The plain `onnx-community/whisper-*` exports throw on any request for word timings** — *"Model outputs must contain cross attentions"*. The `_timestamped` variants work and are 23 KB *smaller*. Without this, `WhisperBrowserSTTProvider` would have advertised `wordTimestamps: true` and failed on every single utterance.
4. **A `max_new_tokens` floor I added made recognition worse.** The reasoning was sound — `_call_moonshine` computes `Math.floor(seconds) * 6`, which really is 0 under a second, and "yes"/"no"/"stop" are all under a second. Running it: a 0.48 s "Yes." transcribes correctly at a budget of 0, and **the floor made Moonshine answer "Yes, yes, yes."**, which is exactly the repetition the paper's heuristic exists to prevent. **The fix was worse than the bug and the bug did not exist.**

**Numbers 3 and 4 were found by running the thing, and would not have been found any other way.** Both were already written into code, one into a shipped provider's capabilities and one into a comment explaining itself confidently. The live check is a closed loop with no fixture and no human — **Kokoro speaks a known sentence and the recognisers write it down**, so word error rate is computed against the text that was spoken rather than eyeballed. Both models: **0% WER**, Moonshine six times faster (118 ms against 754 ms) and Whisper returning 9 and 16 word times.

**The same check demonstrated what unconverted audio actually does**, which I had also overstated. At 24 kHz read as 16 kHz — 1.5x — both models are perfectly fine. At **48 kHz read as 16 kHz, which is what a browser microphone gives you**, Moonshine returns nothing and Whisper returns *"I'll spawn on your top of your ears for cash."* No error either time. The comment now carries the table instead of the adjective.

**Two smaller things worth keeping.** The consent-screen arithmetic had the same shape as yesterday's Kokoro error and was caught the same way: summing a Hugging Face listing's JSON overstates `whisper-base` by 1.63 MB, because transformers.js fetches five specific config files and not `vocab.json`, `merges.txt` or three others sitting next to them. Downloading into an empty cache settled it, and the rule that reproduces both measured totals to the byte is what makes the un-downloaded rows derived rather than guessed. And `signal.ts` exists for one function, because TypeScript narrows `readonly aborted: boolean` and *keeps* the narrowing — so a second check in the same scope is rejected as impossible, on the one property in the codebase whose whole purpose is to change under you.

**Lane: architect-direct, and this is the second in a row against a plan that says `owner: aider`.** The justification is real — a brief carrying those four facts would have *been* the implementation, and one without them would have shipped the broken Whisper — but twice is a pattern rather than an exception, and it is flagged in the brief rather than left to be noticed.
