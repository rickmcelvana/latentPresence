**The finding was a default, and my first conclusion was wrong.** The first pass said 100k rows was impractical: insert throughput collapsed and an `ALTER TABLE … ADD VECTOR INDEX` was still running after six minutes. 768 float32 is 3072 bytes a row, so 100k rows is 307 MB of vectors against the stock **16 MB** `mhnsw_max_cache_size` — below the working-set size the index cache thrashes and what you are timing is disk, not search. Rick raised it to 2 GiB (and the buffer pool to 4 GiB) and restarted; same binary, same fixture, same rows, **7.52 ms median became 1.42 ms** and 100k went from unreachable to eight minutes. It is `GLOBAL`-only, so no application user can set it and the product can never detect or fix it from inside. That makes it a deployment note with teeth: the default will make a user's memory store feel broken for reasons nothing in the app can explain.

**Two measurement failures worth remembering, both mine.** The synthetic fixture was `sin(seed·k + i·k₂)`; sine is periodic, so seed 1,000,020 collided with seed 6,701 and the benchmark reported `distance=0.000000` — a probe identical to a stored row is the easiest possible query for a nearest-neighbour index, and it was one commit from the write-up. Replaced with SplitMix64 per dimension, with that exact pair as a test. Then the entire 100k run was taken while the server's own update agent installed a kernel; Rick caught it before the reboot and moved the agent off the box. None of those numbers survive — everything in the write-up was re-taken on an idle server. ### Writing the brief found four bugs; reviewing the run found a fifth
The four were found before Aider ever ran, by building the reference instead of describing it: digits before a period are a list marker only when the run starts a line, not inside `3.14.`; CJK terminators must not require following whitespace or Japanese never splits at all; a fence edge has to force a boundary because no terminator separates code from the prose after it; and a tag left pending when a chunk came out empty was silently dropped. Same shape of risk between `selfSpacingTerminators` and `terminators`. Fixed by exporting the sets and asserting both against the protocol in the test — the pattern `transition.test.ts` already uses with `conversationEventTypes`.

**The method lesson, which is worth more than the fix.** Verifying reference code compiles and passes proves it is *self*-consistent; it cannot prove the code agrees with a value it merely copied from somewhere else. **Any future brief whose reference duplicates a protocol enum, a config value or a fixture should carry the drift test in the brief** rather than wait for review. That is the second brief-writing lesson in two tasks, after P1-T03's "say how the test narrows a nullable".

### The P1-T04 drift lesson paid for itself one task later
kokoro-js exports `KokoroTTS`, `TextSplitterStream` and `env` from its package root and **not `VOICES`** — the voice table is reachable only through a *loaded* model, and the settings UI has to list voices before the consent screen that precedes a 325 MB download (ADR-09). So the table had to be copied, which is precisely the situation last session's lesson describes. `voices.test.ts` parses the installed bundle and fails if the ids drift. Fifteen lines, written before anyone could forget.

Two other things the surface read caught, neither of which would have failed loudly: **`list_voices()` returns `void`** — it prints a table, so a `listVoices()` built on it would have returned nothing, silently — and Kokoro-FastAPI writes its streaming `wav` through PyAV, so **the `data` chunk size in the header cannot be final**. The parser treats `0` and `0xffffffff` as "read to the end" and every other value as an upper bound, with tests for both.

**And one honest gap, stated rather than buried.** Kokoro's default is `fp32` because that is the precision Spike A measured — 325 MB on first run, against 86 MB for `q8`. Nobody has compared them for *synthesis* quality; Spike A's q8 finding was about Moonshine recognition, not Kokoro. The default is the measured one and the question is open.
