# P0-T04 Spike A: browser voice loop latency — brief

Owner: main (architect-direct). Depends: P0-T01, P0-T02b. ADRs: 01, 06, 09.
Surface facts: `docs/SURFACE.md`, "Browser voice stack", 2026-09-08.

## The question

Can a browser do mic → VAD → STT → LLM → TTS inside the latency budget, on Rick's machine, with
models the user downloads themselves? RESEARCH §3.3 puts the target at **first audio under 800 ms
after end of turn**. The LLM is not in this spike, so the number to beat here is what is left after a
model call: everything except the LLM should fit in roughly **400 ms**.

If it does not, ADR-01 (browser-first) and ADR-06 (cascaded pipeline) are both in question, which is
why this is a Phase 0 spike and not a Phase 1 task.

## What gets built

A dev-only route, `/spike/voice`, in `apps/web`. It is throwaway measurement code, not the product:
P1-T01 through P1-T08 build the real pipeline behind the `packages/protocol` ports. The spike exists
to produce numbers and a go/no-go, and to be deleted or promoted afterwards.

```
apps/web/src/spikes/VoiceLoop.tsx        the page: consent, controls, results table
apps/web/src/spikes/consent.ts           the model manifest (id, size, licence, source)
apps/web/src/spikes/vad.worker.ts        Silero VAD on onnxruntime-web
apps/web/src/spikes/stt.worker.ts        Moonshine tiny on transformers.js
apps/web/src/spikes/tts.worker.ts        Kokoro on kokoro-js
apps/web/src/spikes/metrics.ts           the timing model, and its tests
apps/web/src/spikes/metrics.test.ts
```

Loaded with a dynamic `import()` behind `import.meta.env.DEV`, so `pnpm build` never pulls the
libraries or the route into the production bundle. Verify that: the spike must not change
`apps/web/dist` size meaningfully.

## Consent comes first (ADR-09, hard rule)

**Nothing fetches a weight before the user has seen its size, licence and source.** The spike is not
exempt: it is the first thing in this repo that downloads a model, so it is where the pattern gets
set for P1-T13.

The consent screen lists, from `consent.ts`:

| Model | Repo | Licence | Download |
|---|---|---|---|
| Silero VAD | `onnx-community/silero-vad` | MIT | 2.24 MB |
| Moonshine tiny | `onnx-community/moonshine-tiny-ONNX` | MIT | 28.18 MB |
| Kokoro 82M | `onnx-community/Kokoro-82M-v1.0-ONNX` | Apache-2.0 | 86.03 MB |

with the total and a link to each repo. No fetch, no worker start, no `from_pretrained` until the
button is pressed. A test asserts the manifest carries all four fields for every entry, because an
entry missing its licence is a consent screen that cannot do its job.

## The pipeline

**Mic.** `getUserMedia({ audio: { channelCount: 1, echoCancellation: true, noiseSuppression: true } })`
into an `AudioWorklet` that emits 512-sample frames at 16 kHz. Resample from the device rate; do not
assume 16 kHz, and record what the device actually gave.

**VAD.** Silero VAD directly on `onnxruntime-web`, in a worker. Not `@ricky0123/vad-web`: it brings a
second ONNX Runtime (SURFACE 2026-09-08). Feed 512-sample frames, carry the recurrent state between
calls, threshold with hysteresis — enter speech above ~0.5, leave below ~0.35 — and a silence
hangover to call end-of-speech. **The hangover is part of the measurement, not part of the latency:**
record end-of-speech as the frame where speech actually stopped, not the frame where the timer
expired, and report the hangover separately. Conflating them makes the pipeline look slower than it
is and hides the one number Smart Turn v3 (P0-T07) is meant to improve.

**STT.** Moonshine tiny through the `automatic-speech-recognition` pipeline, in a worker, given the
buffered utterance at end-of-speech. Both `device: 'webgpu'` and `device: 'wasm'`, switchable, since
the go/no-go differs per backend.

**TTS.** Kokoro through `kokoro-js`, in a worker, fed the transcript **echoed straight back** — no
LLM in this spike. Streaming if `kokoro-js` supports it; if it only returns a finished buffer, that
is itself a finding, because the 800 ms budget assumes streaming TTS.

**Out.** Play through an `AudioContext`. First audio is when the first buffer is *scheduled to
start*, not when `generate()` resolved.

## What to measure

Per utterance, in `metrics.ts`, from one monotonic clock (`performance.now()`):

| Mark | Meaning |
|---|---|
| `speechStart` | VAD crossed into speech |
| `speechEnd` | last frame of speech, before the hangover |
| `vadSettled` | hangover expired and the utterance was closed |
| `sttFirstResult` | first text back from Moonshine |
| `sttDone` | final transcript |
| `ttsFirstAudio` | first sample scheduled on the output |

Report `speechEnd → ttsFirstAudio` as the headline, with the breakdown beside it, and the hangover
called out as tunable. Also record: model load time per model, cold vs warm, the device sample rate,
the backend actually used, and `performance.memory.usedJSHeapSize` before and after (noting it
excludes wasm memory, which is where most of it lives — record `performance.measureUserAgentSpecificMemory()`
if the browser offers it, otherwise say so).

Ten utterances minimum per backend, reported as median and worst, not a single lucky run. A "copy
results as Markdown" button, so the numbers reach the write-up without being retyped.

## Tests

`metrics.test.ts` only. The audio path cannot be unit-tested without fixtures and this is a spike, so
the tests cover the thing that would silently make every number wrong:

1. The timing model computes each interval from the marks, and `speechEnd → ttsFirstAudio` excludes
   nothing that happened in between.
2. Out-of-order or missing marks produce an explicit "incomplete" result rather than a plausible
   number. A dropped `sttDone` must not read as a fast turn.
3. Median and worst over a set of runs, including the even-count case.
4. The consent manifest has an id, size, licence and source URL for every model.

## Done when

1. `docs/spikes/A-voice-loop.md` records, from Rick's machine: median and worst
   `speechEnd → ttsFirstAudio` for WebGPU and for WASM, the per-stage breakdown, model load times,
   memory, the device sample rate, and the browser and GPU it ran on.
2. It states a go/no-go against the 800 ms budget, and if no-go, which stage is at fault.
3. `pnpm gate` green, and `pnpm build` output is not meaningfully larger than before the spike.
4. Nothing downloads before consent — verified by watching the network panel with the page open and
   the button untouched.

## Notes for whoever reads this later

- The spike is allowed to be ugly. It is not allowed to be dishonest: no number that was not
  measured, no median over three runs presented as typical, no "first audio" that is really
  "generate() returned".
- If WebGPU is unavailable or falls back silently, say so in the write-up rather than reporting the
  WASM number twice.

## Closed 2026-09-08

Done. `docs/spikes/A-voice-loop.md` carries the numbers and the go/no-go.

The 800 ms figure this brief was written against no longer stands: ADR-20 replaced it with
two numbers, because the measured pipeline exceeded it with no model call in the loop. The
brief's own derived target — "everything except the LLM should fit in roughly 400 ms" —
turned out to be the useful one, and the measured 435 ms is what ADR-20's 500 ms budget is
built on.

Four defects were found on the way and are recorded in the write-up: q8 recognition broken
on WebGPU, `kokoro-js` `stream()` never returning, the production bundle shipping 21 MB of
ONNX Runtime for an unreachable route, and turn marks kept in one slot while turns overlap.
