# P0-T06 Spike C: companion and MariaDB vector — brief

Owner: main (architect-direct). Depends: P0-T01. ADRs: 04, 05, 17 (amended 2026-09-09).
Surface facts: `docs/SURFACE.md`, "MariaDB vector, and the dev servers", 2026-09-09.

## The question

ADR-05 puts the memory store in MariaDB with a vector index, and ADR-17 designs the memory
kernel around one batched retrieval per turn on the assumption that a round trip is
expensive. `docs/LLM-PLAN.md` gives per-turn retrieval a **100 ms budget**. Nothing has
tested any of it.

Three things this answers:

1. **Does the schema work at scale?** `VECTOR(768)` with an MHNSW index, at 10k and at
   100k rows — not at three.
2. **Does retrieval fit in 100 ms**, and on which network? The two hosts differ by two
   orders of magnitude and that is the whole story.
3. **Does the index get used?** Not "is it fast", but "does `EXPLAIN` name it" — because
   the fast-looking wrong answer is a full table scan.

## What is already known, and must not be re-derived

Read the surface entry first. Four things shape the work:

- **`192.168.40.101` is MariaDB 11.8.8** and does everything needed. `10.0.0.1` is
  10.11.18 and has no vector support at all.
- **The network term is measured**: **0.43 ms p50 on the LAN, 39.8 ms p50 over the
  tunnel**. Both belong in the write-up. A LAN figure alone would say the network is free,
  which is true in exactly one deployment.
- **A `VECTOR` column crosses the wire as `MYSQL_TYPE_VAR_STRING` with the binary flag** —
  little-endian `f32`, 4 bytes per dimension, no length prefix. sqlx needs **no custom
  `Type` impl and no `::text` cast**: `Vec<u8>` out, `&[u8]` in. Binary binding is verified
  to work, and 768 dimensions is 3072 bytes binary against 7–8 KB of JSON text.
- **A query whose distance function disagrees with the index falls back to a full table
  scan**, silently. `DISTANCE=cosine` on the index, `VEC_DISTANCE_COSINE` in the query,
  and `EXPLAIN` to prove it.

Server defaults to report against: `mhnsw_ef_search = 20`, `mhnsw_max_cache_size = 16 MB`,
`mhnsw_default_m = 6`.

## What gets built

```
companion/crates/server/src/db/mod.rs        pool, health, RTT probe
companion/crates/server/src/db/chunks.rs     insert and top-k, binary vectors
companion/crates/server/migrations/          sqlx migrations, checked in
companion/crates/server/src/bench.rs         the 10k / 100k benchmark, behind a flag
packages/protocol/src/memory.ts              the wire contract for the two endpoints
```

sqlx 0.9.0 with the `mysql`, `runtime-tokio` and `migrate` features. The migration:

```sql
CREATE TABLE chunks (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  doc_id     BIGINT UNSIGNED NOT NULL,
  text       MEDIUMTEXT NOT NULL,
  embedding  VECTOR(768) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY (doc_id),
  VECTOR INDEX (embedding) M=8 DISTANCE=cosine
) ENGINE=InnoDB;
```

`NOT NULL` on the vector is required, not stylistic, and a table may carry only one vector
index.

Two endpoints, both on the companion, both taking and returning the binary vector form:
insert a batch of chunks, and query top-k by `VEC_DISTANCE_COSINE`. The TS client is the
typed contract in `packages/protocol` plus a thin fetch wrapper; it does not need to be a
full provider yet — P4 builds that.

## Measuring honestly

**Separate the network from the work.** Three numbers per configuration, never one:

| | |
|---|---|
| `SELECT 1` round trip | the network term, on its own |
| Query time server-side | from the same connection, warm |
| End to end | what a turn actually waits for |

The first is already measured for both hosts; take it again in the same run so the three
are comparable rather than quoted from different days.

**Report a distribution, not a mean.** Median and p95 over at least 100 queries at each
row count, with the warm-up discarded and said so. A mean retrieval latency hides the tail,
and the tail is what a person notices in a conversation.

**Prove the index.** `EXPLAIN` on the top-k query at both row counts, quoted verbatim in
the write-up. `key: embedding` or the number is meaningless.

**Say what recall was traded for it.** `mhnsw_ef_search` defaults to 20. A fast number at a
low `ef_search` is a fast number for a worse answer, so report the setting beside the
latency, and if there is time, one sweep at a higher value to show the shape of the trade.

### The 100k case is the one with a finding in it

768 float32 is 3072 bytes a row, so **100k rows is roughly 307 MB of vectors against a
16 MB `mhnsw_max_cache_size`**. The index graph will not sit in cache. That ratio is what
the 100k case is really testing, and if latency degrades between 10k and 100k, that is the
first place to look — not the network, not the query.

## Tests

Unit tests never need a running database (`docs/WORKFLOW.md`). So:

1. **Vector encoding round trip**, in Rust, with no database: `&[f32]` → little-endian
   bytes → `&[f32]`, including a non-power-of-two length and a negative value. This is the
   piece that would silently corrupt every embedding, and the wire format is fixed
   (`docs/SURFACE.md`), so it can be asserted against known bytes rather than against
   itself.
2. **Dimension mismatch is refused before it reaches the server**: 767 or 769 floats is an
   error with a typed message, not a query that fails 40 ms later with a driver error.
3. **The TS contract parses and rejects**, as the other protocol schemas do.
4. The benchmark's own statistics — median and p95 over a known set — reuse the model from
   `frame-rate.ts` rather than growing a second one, or move it somewhere shared.

Live checks are producer-run and go in the write-up, not the gate.

## Done when

1. `docs/spikes/C-mariadb-vector.md` records, at **10k and 100k rows**: insert throughput,
   query median and p95, the `SELECT 1` round trip taken in the same run, the `EXPLAIN`
   output, `mhnsw_ef_search`, and the machine and server versions.
2. It states plainly **whether the 100 ms per-turn retrieval budget holds** — on the LAN,
   and by arithmetic over a 39.8 ms tunnel — and what that means for ADR-17's one-call
   rule.
3. CI runs the same schema and query against a `mariadb:11.8` service container, so the SQL
   is covered by the gate even though the numbers are not.
4. `pnpm gate` green, including `cargo fmt`, clippy `-D warnings` and `cargo test`.
5. No secrets in logs, config or error strings. `DATABASE_URL` is read from `.env` and
   never printed — a connection error must not echo the password back.

## Notes for whoever reads this later

- **No Docker on the dev box.** The compose file in `companion/dev/` is for other people
  and for documentation; it cannot be tested here, so do not claim it works. CI's service
  container is the thing that is actually exercised.
- Write the benchmark so it can be pointed at either host by `DATABASE_URL` alone. The
  interesting comparison is the same code over two networks.
- Cleaning up matters: 100k rows of 3 KB vectors is 300 MB in a database Rick has to live
  with. The benchmark creates its table with a distinct name and drops it, and says in the
  write-up that it did.
