# P0-T08 Spike E: the Tauri shell — brief

Owner: main (architect-direct). Depends: P0-T04 (Spike A), P0-T05 (Spike B), P0-T07 (Spike D).
ADRs: 01, 07. Surface facts: `docs/SURFACE.md`, "Tauri 2, for P0-T08 Spike E", 2026-09-09.

## The question

ADR-07 targets Tauri 2 with Windows first, and names the risk in its own text: **WebKitGTK
is the risk**. It also pre-writes the answer if the risk lands — "if Tauri blocks a
platform later, that platform ships as `companion + Chrome/Edge`". So this spike does not
need a new decision. It confirms ADR-07's Linux path, or it triggers a clause ADR-07
already contains.

**Does Linux ship as a Tauri app, or as companion + Chrome?**

## The whole spike turns on one check, and it takes five minutes

Three Phase 0 results depend on WebGPU:

| Spike | The dependency |
|---|---|
| A (voice) | 947 ms end to end on WebGPU. Synthesis alone on wasm: **3779 ms** |
| D (turn) | int8 will not load on WebGPU at all; **fp32/WebGPU is the go configuration** |
| B (avatar) | 120.5 fps with a GPU path |

If the Tauri webview on Linux has no `navigator.gpu`, the Linux voice pipeline is not
merely slower — it is outside ADR-20's 500 ms budget **by a factor of seven**, and no
amount of shell engineering closes that. The answer is then "companion + Chrome" and the
spike is essentially over.

**So do this first, before building anything past a window that loads a page.** Inside the
Tauri webview, not in a browser on the same box — a Chrome on that machine proves nothing
about WebKitGTK:

```js
({ webgpu: !!navigator.gpu,
   adapter: navigator.gpu ? !!(await navigator.gpu.requestAdapter()) : false,
   webgl2: !!document.createElement('canvas').getContext('webgl2'),
   worklet: !!(window.AudioContext && AudioContext.prototype.audioWorklet !== undefined),
   media: !!navigator.mediaDevices?.getUserMedia,
   sab: typeof SharedArrayBuffer !== 'undefined' })
```

`navigator.gpu` existing is not enough — **`requestAdapter()` must return an adapter**. A
webview can expose the namespace and then fail to find a device, and Spike B already caught
Chrome ignoring `powerPreference` on Windows, so treat the namespace as an advertisement
and the adapter as the fact.

Record `pkg-config --modversion webkit2gtk-4.1` beside the result. A bare yes or no with no
version against it is worthless in six months.

## What is already known, and must not be re-derived

Read the surface entry first.

- **Versions**: `@tauri-apps/cli` 2.11.4, `@tauri-apps/api` 2.11.1, `tauri` crate 2.11.5,
  `wry` 0.57.0, all verified against the registries on 2026-09-09.
- **The webview package is `4.1` on every distribution**, not `4.0` — that is the soup2
  generation Tauri left in 2.0.0-alpha.3. The exact package lists per distro are in the
  surface entry; Rick installs them before the session starts.
- **WebGPU on WebKitGTK is not established by any source consulted.** The working group's
  implementation-status page lists WebKit's WebGPU as enabled on macOS, iOS, iPadOS and
  visionOS — every one an Apple platform — and does not mention WebKitGTK or WPE at all.
  Absence from a table is not absence in the port. **Go and measure it.**

## What gets built

```
apps/desktop/                 Tauri 2 shell
apps/desktop/src-tauri/       the Rust side
docs/spikes/E-tauri.md        the write-up
```

The shell points at the existing `apps/web` dev server and runs the three spike routes that
already exist — `/spike/voice`, `/spike/avatar`, `/spike/turn`. **Nothing new is built to
test**: the point is to run known-good pages in an unknown container and see what the
container takes away.

### A workflow trap to handle deliberately

`pnpm gate` runs Rust as `cargo … --manifest-path companion/Cargo.toml --workspace`. A new
crate under `apps/desktop/src-tauri` is **not in that workspace and will not be gated** —
it will compile in CI never, and fmt/clippy will not see it. Decide explicitly and say so
in the write-up:

- add it to the gate (a second `--manifest-path`, or make `companion` and the shell one
  workspace), or
- leave it out on purpose because Phase 8 owns the desktop app and a Phase 0 spike should
  not slow every gate by building a webview.

Either is defensible. Silently shipping an ungated crate is not.

## Measuring honestly

- **Per OS, per capability, in a table.** Windows/WebView2 and Linux/WebKitGTK. macOS is
  deferred by ADR-07 and is not a gap in this spike.
- **The capability probe runs inside the shell.** Repeat it in Chrome on the same box only
  as a control, and label it as one.
- **A spike page that "works" is not a result. Say what it measured.** `/spike/voice`
  prints its own numbers; if it runs at all on WebKitGTK, the write-up carries the timings,
  not the word "works".
- **Failures get their error text quoted**, the way Spike D quoted the int8
  `DequantizeLinear` failure. "Didn't work" is not a finding; the error is.

## The two-sitting shape

The Linux leg is the one with the decision in it and Rick's box is Linux, so it goes first.
**The Windows/WebView2 leg needs Rick back on Windows** and can be a second sitting — the
shell will already exist by then, so it is a run rather than a build. The spike does not
close until both are in the table; say so in the write-up rather than implying Windows was
covered.

WebView2 is Chromium, so the expectation is that Windows passes and Linux is where the
information is. Expectations are not results — run it.

## Done when

4. `pnpm gate` green.

## Notes for whoever reads this later

- Rick's Linux box is the same hardware class as the Windows one (RTX 5060 Ti), so a
  frame-rate difference between the two is the webview, not the GPU. That makes this a
  cleaner comparison than it usually is — use it.
- Nothing about the memory store is in scope here. Spike C is closed; `DATABASE_URL` is not
  needed for this task.
- If WebGPU is missing on WebKitGTK, resist the urge to go and fix it. The finding is the
  deliverable, ADR-07 already says what happens next, and Phase 8 owns the shell.
