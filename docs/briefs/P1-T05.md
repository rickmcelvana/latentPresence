# Brief P1-T05 — TTS providers

Owner: **main**, not aider — see "Lane decision" below, which is the first thing worth reading.
Depends: P1-T04 (the chunker whose output this is asked to say). ADRs: 09 (consent before any weight moves), 11 (where the worker lives), 20 (the 500 ms budget), 24 (new, proposed — how audio crosses).
Interface: **none changed.** `TTSProvider`, `TtsRequest`, `TtsVoice`, `TtsCapabilities` and `SpokenAudioChunk` were already in `packages/protocol` and none of them moved.

## Lane decision

`docs/LLM-PLAN.md` marks P1-T05 **owner: aider**, and it landed architect-direct instead. The reason is a rule this repo already wrote down.

The established rhythm for an Aider task is: the architect builds the implementation in the tree, gates it, removes it, embeds it in the brief as reference code, and Aider transcribes it back. That has worked four times running, byte-identically. But `docs/WORKFLOW.md` names the exception in the same breath:

> **Architect-direct** when the implementation is small, interface-shaped, or **already written and verified**. Sending it out cannot change the outcome.

and CLAUDE.md says it flatly: **"Finished, verified code never goes through Aider."**

By the time the reference for this task existed it was thirteen files and about 1700 lines across two packages, gated green. Removing working code so it could be retyped would have spent a run of Rick's time and an Aider transcription to arrive back at the same bytes, with a fresh chance of drift and no context saved — the context was already spent writing it. Aider's whole justification is saving architect context (ADR-13), and there was none left to save.

So this brief is **a record rather than a set of instructions**: the spec, the verified surfaces, the decisions, and what is deliberately not here. The code is in the tree.

## Goal

After this task `packages/providers/tts/` can turn one `SpeechChunk` of text into audio, through a model in the browser or a server the user runs, behind one interface, with capability flags that tell the truth about what each one cannot do.

## The decisions worth arguing with

### Why the worker is in `ml-web` and the provider is in `providers`

ADR-11's layout says `packages/ml-web/` is "worker wrappers for transformers.js / onnxruntime-web models" and `packages/providers/` is the adapters. Splitting on that line costs one new package edge (`providers` → `ml-web`) and buys the thing that makes this testable: **the provider imports types from `ml-web` and never the worker**, so the whole conversation with it — request ids, the held-back final chunk, cancellation, a failed load — runs in node against a fake port. P1-T06 does the same thing again with Moonshine and Whisper a task later, which is why the pattern was worth establishing rather than improvising.

### Why the copied voice table has a drift test

kokoro-js exports `KokoroTTS`, `TextSplitterStream` and `env` from its package root, and **not `VOICES`**. The table is reachable only through a loaded model — and the settings UI has to list voices *before* the consent screen that precedes downloading 325 MB (ADR-09). So the table is copied.

A copy that nothing checks is how a provider goes quietly wrong, and that is exactly P1-T04's closing lesson: *verifying reference code proves it self-consistent, never that it agrees with a value it copied.* `voices.test.ts` therefore parses the installed `kokoro-js` bundle and fails if the ids drift. First application of that lesson, and it cost about fifteen lines.

### Why `wav`, and why nothing streams

ADR-24, in full. Short version: `decodeAudioData` is a DOM API and would make every test a browser test; `pcm` is headerless so its rate would have to be a guess; compression buys nothing for one sentence of 24 kHz mono. And the intra-sentence streaming that `stream_format: 'sse'` offers is not worth base64 framing over a partial container when P1-T04 has already made the unit of latency a sentence.

### Why Kokoro reports `emotionHints: false`

There is no emotion or style parameter on kokoro-js's surface at all — only `speed`, which `TtsRequest` carries in its own right and which is honoured. Mapping `EmotionHint.energy` onto a speed change was considered and rejected: nobody has measured what it sounds like, and a provider that quietly reinterprets a hint is worse for the affect engine than one that says it cannot take it. `TtsCapabilities.emotionHints` exists precisely so P3 can compensate rather than assume.

The server adapter *can* honour a hint, through OpenAI's verified `instructions` field — off by default, because a self-hosted server may reject a body field it does not know.

### Why neither real provider has word timings

Neither surface returns them (`docs/SURFACE.md`, 2026-09-12). Both report `wordTimestamps: false`, which is the branch `packages/protocol/src/capabilities.ts` already anticipated in writing: *"word timings, for instance, become wawa-lipsync analysis when the TTS has none."* **P2's viseme scheduling should plan on analysis, not timings.** `FakeTTSProvider` supplies timings that add up so the other branch is still testable.

### The one invariant every provider holds

**Exactly one chunk per `synthesize` call carries `isFinal: true`, and it is the last one** — including when the call is cancelled, and including when the backend produced no audio at all. The audio output queue (P1-T08) releases on that flag, and a path that can skip it is a path that hangs the character mid-turn.

## Manual verify

No click-through — there is no UI. There is one cheap check that proves the server adapter against real bytes rather than hand-built ones, and it needs no app:

1. With a Kokoro-FastAPI (or any OpenAI-compatible TTS) at `$BASE`:

```bash
curl -sS "$BASE/v1/audio/speech" -H 'content-type: application/json' -d '{"model":"kokoro","input":"Hello there, this is a test.","voice":"af_heart","response_format":"wav","speed":1}' --output /tmp/speech.wav
```

2. Check the adapter agrees with the file:

```bash
node --experimental-strip-types -e "import('./packages/providers/src/tts/wav.ts').then(async (m)=>{const b=new Uint8Array((await import('node:fs')).readFileSync('/tmp/speech.wav'));const d=m.decodeWav(b);console.log(d.sampleRate,'Hz',(d.samples.length/d.sampleRate).toFixed(2),'s',d.channels,'ch')})"
```

Expect 24000 Hz, a duration that matches the sentence, 1 channel. A `WavParseError` here is a real finding and belongs in the session log.

3. `GET $BASE/v1/audio/voices` — note which of the two shapes it returns. Both are handled; which one appears in the wild is worth recording.

## Out of scope, deliberately

- **Wiring.** Nothing calls these yet. P1-T08 (output queue and barge-in) and P1-T10 (settings) are the consumers.
- **Measuring `maxChars`.** P1-T04 handed this task the job of replacing its `maxChars: 200` starting value with a measurement against real TTS latency. **It is not done**, because the measurement needs a live Kokoro run on a WebGPU box and there is no play-out path to run it through. It moves forward to P1-T08 with the live verification, and is on Rick's backlog with the rest.
- **The `kokoro-js` entry in `apps/web/vite.config.ts`'s spike guard.** It stays, and the build is still green, because nothing in the app imports these providers yet. The guard's own docstring says it is the thing to delete when P1 puts synthesis into the product for real; that is P1-T08's to do, knowingly.
- **Compressed formats.** ADR-24.
- **Backchannels.** P1-T09 depends on this and pre-synthesises its own.
- **Whether `fp32` is the right default.** It is what Spike A measured, at 325 MB. `q8` is 86 MB and would be a much kinder first run. Nobody has compared them for *synthesis* quality — Spike A's q8 finding was about Moonshine recognition, not Kokoro — so the default is the measured one and the question is open.
