# P1-T08 — Audio output queue and barge-in

- **lane:** main
- **status:** not started
- **written:** 2026-09-13, as a handoff, the same day P1-T07 landed. Nothing below has been
  built; everything marked *verify* has not been checked.

## The plan line, and what it is hiding

> *AudioWorklet playback queue; on user speech start, fade out in 100 ms, cancel LLM stream,
> mark transcript with the spoken prefix.*
> *Done when: manual test shows no audio clicks and the transcript reflects only the words
> that were heard.*

Three of those clauses lean on something the repo doesn't have yet:

1. **Nothing streams an answer into speech today.** The LLM providers, the chunker and the
   TTS providers all exist, but nothing connects them. `PROJECT.md` still says "nothing
   calls it yet" about the chunker. "Cancel LLM stream" needs something that owns the
   stream. That orchestration is this task's, because barge-in can't be tested without it.
2. **"The words that were heard" has no word timings behind it.** Neither real TTS provider
   returns any (P1-T05), so the spoken prefix has to be *estimated* from how much audio
   played. The estimate is the product decision here, and it can be measured.
3. **"On user speech start" will interrupt the character with its own voice.** Spike A's
   transcripts had the previous reply in them, because the microphone heard the speakers
   with browser echo cancellation on (`docs/spikes/A-voice-loop.md`, *The microphone hears
   the answer*). A fade on the first Silero frame at `speechOn` fires on exactly that.

## Why this is `main` and not `sub`

Most of the correctness here comes from facts that have to be measured or read out of a
dependency:

- how Vite bundles an AudioWorklet module from a workspace package;
- what `AudioContext.outputLatency` reports;
- whether Chrome's echo cancellation covers Web Audio output;
- whether Kokoro `q8` is sane on WebGPU.

On top of that come two judgement calls against ADR-20's budget: the barge-in trigger and
the prefix estimate. **One piece is `sub`-shaped**: the dev harness page, once the queue
and the controller are green. Hand that out rather than spending architect context on JSX.

## Proposed shape

Follow P1-T07's split: logic with no audio API in `packages/core`, thin browser shells
elsewhere, and a live check for what the gate can't see.

**`packages/core/src/playback/`: the queue's bookkeeping, no Web Audio.**

- Keep an ordered list of what was enqueued: sentence index, text, sample count and rate.
- Map a played-sample count back to sentence boundaries, which drives
  `assistant.audio.started`/`ended` from the *playhead* rather than from enqueue time.
- Compute the fade gain curve.
- Turn "N samples heard" into a spoken prefix.
- All of it tested against scripted playhead reports, as `TurnDetector` was against
  scripted probabilities.

**`packages/core/src/reply/`: the reply controller.**

- Stream `LlmStreamChunk`s into `SentenceChunker`, then into `TTSProvider.synthesize` per
  chunk, then into the queue, all under **one** cancellation.
- Barge-in aborts it. The LLM, the synthesis in flight and the queued audio all go on one
  call, and the result reports what was heard.
- Type it against the protocol's `LLMProvider` and `TTSProvider` interfaces. Core can't
  import `packages/providers`, which depends on core, so core's tests use small scripted
  fakes. The integration test over the real `FakeLLMProvider` and `FakeTTSProvider` goes in
  providers, as P1-T07's end-to-end overlap test did.
- Synthesise **sequentially, as sentences arrive**. D-12 measured synthesis at ~44x faster
  than speech on the server path, so concurrency buys nothing measurable. Check the browser
  path's ratio before believing that holds there.

**The browser half: the worklet processor plus the `AudioOutPort` driver.**

- The obvious home is beside `BrowserSileroVad` in `packages/providers`. It's a port
  implementation in the same sense. Put the processor file wherever the bundling question
  (below) says it can live.

**A dev harness route that replaces `/spike/voice`.**

- Wire the promoted pieces together: `BrowserSileroVad`, `TurnDetector` with
  `SmartTurnJudge`, `speculativeTranscription`, a TTS provider, the queue, and
  `FakeLLMProvider` replaying a long scripted answer.
- A fake LLM is the right default. A barge-in test wants a reply long enough to interrupt,
  the same every time, with no key.
- The page shows each turn's generated text against its spoken prefix.
- Spike A's own workers, `audio.ts` `Playback` and the `spike-capture` guard needle go.
  `PROJECT.md` said Spike A goes when P1-T08 closes, and this is how that happens without
  losing the only page that plays synthesis. Keep Spike A's timing table if it still earns
  its place, now reading the real pipeline.

**Not this task:**

- the settings UI (P1-T10);
- the transcript panel (P1-T11);
- the real consent screen (P1-T13). The harness reuses the spike's consent path until then.

## Decisions the task has to make

Each gets the recommended option taken and a `proposed` ADR if it departs from the plan
line, per `CLAUDE.md`.

### 1. What triggers barge-in

**Recommended: two stages.**

- **On `speech-start`, duck.** Ramp the gain down to roughly −12 dB over ~30 ms. It's
  reversible and costs nothing if wrong.
- **Commit** when speech has lasted `bargeInMs`: the 100 ms fade to silence, abort the
  reply, emit `assistant.interrupted`.
- If speech stops before `bargeInMs`, un-duck and carry on. Then a cough, a "mm-hm" or the
  character's own echo never throws the answer away.
- **`bargeInMs: 0` is exactly the plan's rule**, so the plan line stays reachable by
  configuration.
- Start around 200 ms. It's a dial, and the evidence for its value is the echo measurement
  below, not this brief.

Test before building around it: **does Chrome's echo cancellation cancel audio this page
plays through Web Audio?** Don't assume either way; recollection of which Chrome version
made echo cancellation Chrome-wide is exactly what `docs/SURFACE.md` forbids. Spike A says
it didn't cover *an external microphone next to speakers*. That's one configuration. Rick
runs speakers-on with the mic live, and the harness counts self-interruptions. If echo
cancellation covers it, `bargeInMs` can shrink.

### 2. How "heard" is estimated

**Recommended: estimate the prefix from played audio, and count a word only if its
estimated end was heard.**

- **Heard samples** = frames the worklet actually rendered, minus `outputLatency` converted
  to samples. Don't use what was enqueued, and don't use `currentTime`. The worklet counts
  frames, so it is the only component that knows. **Verify** what `outputLatency` reports
  on wired output against Bluetooth; Bluetooth can be 150 ms or more, which is several
  words.
- **Where a word ends** within a sentence: allocate the sentence's duration across its
  characters in proportion, then snap to word boundaries. It's crude and honest.
- **Before settling for crude, read `kokoro-js`'s `dist`** for per-phoneme durations. The
  model predicts them. If they are reachable through the library's surface, the estimate
  becomes real timings for the browser provider only. Record either way in `SURFACE.md`.
- **Audio in the fade counts as heard up to the fade's midpoint.** Audio while ducked counts
  as heard in full.
- **Tags past the prefix never fire.** P2 reads `InlineTag.offset` against spoken text, so
  a truncated sentence must truncate its tags too.

**Measure it with a closed loop in node, the P1-T06/T07 way** (`pnpm live:bargein`):

1. Kokoro speaks a sentence.
2. Cut it at a sample N chosen at random.
3. Moonshine transcribes the cut audio.
4. Compare its words with the estimator's prefix for N.

Report how often, and by how many words, the estimate runs ahead of what was audible
compared with running behind. Running ahead is the worse error: memory would record the
character saying something the user never heard. **Read the rows, not just the summary**,
per the P1-T07 lesson. Moonshine also needs trailing silence to emit its last word
(`SURFACE.md`, 2026-09-13), so pad the cut before transcribing, or the check measures
Moonshine.

### 3. The port and the machine

- **`AudioOutPort.fadeOut(ms): void` becomes something that resolves when the fade is done
  and reports the played extent.** The machine's `interrupted → listening` teardown timer
  is replaced by that completion. It stays only as the headless path with no `audioOut`
  port. `ports.ts` is core, not protocol, so no ADR is needed; `machine.test.ts` changes
  with it.
- **ADR-25 hands this task a protocol change.** It says the retraction event is "for
  whichever task first wires the detector into the machine". Barge-in on speech start is
  that wiring. Check the consequence in `detector.ts`: **`turn-resumed` is emitted instead
  of a second `speech-start`**. Without a protocol counterpart, a machine in `thinking`
  after a provisional end never hears that the person started talking again.
- **Recommended:** add `user.turn.resumed` to `ConversationEventSchema`, with
  `thinking → listening` in the transition table and an ADR-25 note, architect-owned. Map
  it in the adapter, not by faking a `speech-start`, because P1-T11's transcript needs to
  know it was the same turn.
- **Make ADR-25's "never audible" a guarantee.** ADR-25 argues a retracted turn never costs
  audio because retraction closes at +500 ms and first audio is ~553 ms. That's arithmetic
  on today's path, and a fast cached model on a GPU TTS server could beat it. **The queue
  should hold a reply's audio until the turn's `confirmedAt`.** It costs nothing on the
  measured path and closes the case where it would matter.

### 4. One output context, at what rate

**Recommended:**

- One output `AudioContext` for the session, at **24 kHz**. Both TTS providers produce
  24 kHz today; let the browser resample to the device.
- Resample any other rate before it reaches the queue.
- Don't do what Spike A's `Playback` does and re-create the context on a rate change. That
  is a gap and probably a click.

Watch for:

- **`resample.ts` is linear.** It was fine for 48 kHz → 16 kHz into a recogniser, and is
  unmeasured for speech a person listens to. If a non-24 kHz provider shows up, that's the
  place to look.
- **The capture side runs its own 16 kHz context.** Two contexts in one page is what Spike A
  already did successfully on this machine. Note it if it matters to echo cancellation.

## Clicks: where they come from, and how to see them without ears

"Manual test shows no clicks" deserves an objective check next to Rick's ear.

**The candidates:**

- **A hard stop.** The fade exists for this. Ramp per sample inside the worklet; a gain
  change per render quantum (128 frames) is 5.3 ms at 24 kHz, which is a staircase.
- **An underrun mid-sentence.** The queue empties and output snaps to zero. Ramp down on
  underrun and back up on refill, and count underruns: one in normal speech means the
  controller is starving the queue.
- **Sentence joins.** Measure Kokoro's first and last sample values before assuming its
  output starts and ends at rest.
- **Clipping.** Kokoro peaks at 1.043 (`SURFACE.md`). **Clamp**, in the worklet or before
  it; a 4% hard clamp is distortion, not a click, but it must not wrap.
- **Context start and resume.** The autoplay policy leaves an `AudioContext` suspended until
  a gesture. The harness resumes it on the start button, and a resume with audio already
  queued must fade in.

**In the gate:**

- the fade curve is monotone and per-sample, and reaches exactly zero at `fadeMs`;
- no sample-to-sample step in the queue's output exceeds a bound at a join, an underrun,
  a duck or a fade, over synthetic tones;
- the clamp holds.

**In the browser:**

- tap the output, for example through a recorder worklet, and flag any event point where
  the local step exceeds the 99.9th percentile of steps in steady speech;
- Rick confirms by ear. That becomes **R-2** in `docs/TASKS.md`, which has been waiting on
  exactly this task.

  server's log line, not the client's silence.

## What must not be designed out

- **P1-T09 backchannels** play short clips in user pauses that belong to no reply, and
  never over user speech. The queue needs a way to play a clip outside a reply, and a way
  to refuse to start one while the user is speaking.
- **P2 lip sync** analyses the output with wawa-lipsync and schedules visemes against the
  playhead. Leave a node P2 can attach an analyser to. Expose the playhead position, not
  only sentence events.
- **P1-T11's latency badges** want *turn end to first audio*. That is first rendered frame
  plus `outputLatency`, the same "scheduled to start, not synthesis returned" distinction
  Spike A's `Playback` made.

## Watch for

- **Bundling the worklet** (*verify*). ml-web's workers use
  `new Worker(new URL('./x.worker.ts', import.meta.url))`, a form Vite rewrites.
  `audioWorklet.addModule(new URL(...))` is not the same call and may not be transpiled or
  emitted. Spike A dodged it with a Blob string. Settle it against the production build
  (`pnpm build` plus the build guard), not the dev server, because they differ.
- **The worklet has no `performance.now()`**, and a processor whose `process` returns
  `false` is silently gone for good.
- **Transferable buffers.** Post chunks with their `ArrayBuffer` transferred, as the turn
  drivers do. A transferred chunk is detached on the sender, so the controller must not
  keep reading it.
- **A barge-in during `thinking`** has no audio to fade. It must still abort the LLM and
  any synthesis, and must not emit `assistant.interrupted` with an empty prefix as if
  something had been cut. The transition table already sends `thinking → listening`.
